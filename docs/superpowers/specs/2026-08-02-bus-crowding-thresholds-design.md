# 버스 혼잡도 표시 기준 재설계

작성일: 2026-08-02
상태: 구현 완료. 프로덕션 DB 적용 대기(`scripts/prod_migration_20260802_bus_crowding_distribution.sql`)

## 구현 후 프로덕션 실측 검증 (읽기 전용)

새 집계 SQL(접근 dedup + 등급 분포)을 프로덕션 데이터에 그대로 돌린 결과. 30분 버킷.

| 노선·승차점 | 버킷 | 접근 | 평균 | ≥3 비율 | 새 라벨 | 기존 라벨 |
|---|---|---:|---:|---:|---|---|
| 시흥33 하교 · 한국공학대 | 17:00 | 73 | 2.41 | 47.9% | **매우 붐빔** | 보통 |
| 시흥33 하교 · 한국공학대 | 17:30 | 81 | 2.42 | 45.7% | **매우 붐빔** | 보통 |

| 20-1 하교 · 한국공학대 | 17:00 | 35 | 1.94 | 20.0% | **붐빔** | 보통 |

시흥1은 보정 규칙이 프로덕션에 아직 없어 관측 그대로다. 마이그레이션 적용 후
평일 16~19시에 `매우 붐빔 · 경험 기준`으로 표시된다.

## 문제

17~18시 시흥33 하교(한국공학대 승차)는 실제로 버스가 가득 찬다. 그런데 화면에는
"보통"으로 표시된다. 프로덕션 실측(2026-05-04 ~ 08-02, `bus_crowding_logs` 144만 건)
기준 평일 17시 이 노선의 도착 버스는 **46.6%가 혼잡(≥3)** 이고 p75·p90이 모두 3이다.

원인은 임계값 하나가 아니라 희석이 세 번 겹친 것이다.

| 단계 | 위치 | 효과 |
|---|---|---|
| ① 집계 단위 | `bus_crowding_stats._REFRESH_SQL` | 로그 행을 센다. 같은 차량을 45초마다 재기록하므로 멀리서 잡힌 빈 상태가 과대 대표된다 |
| ② 버킷 해상도 | `crowdingSummary.mergeToTwoHourBuckets` | 16시(1.586)와 17시(2.402)를 합쳐 ≈2.0. 1시간짜리 피크가 조용한 시간과 섞인다 |
| ③ 라벨 임계 | `crowdingPalette.crowdedLabel` (`<2.5 → 보통`) | 2시간 평균이 2.5를 넘는 일은 사실상 없다 |

근본은 통계량 선택이다. `avg_crowded`는 하한이 1이라 "값 1인 버스 절반, 값 3인 버스
절반"이 2("보통")가 된다. 그 2는 실제로 존재한 어떤 버스도 설명하지 않는다. 사용자는
꽉 찬 버스를 기억하는데 화면은 평균을 말한다.

## 실측 근거

평일, 차량 접근 1회 = 1표본(같은 plate의 20분 이상 공백을 경계로 접근을 분리하고
정류장에 가장 가까웠던 관측 1건만 채택).

| 노선·승차점 | 16시 | 17시 | 18시 | 19시 |
|---|---:|---:|---:|---:|
| 시흥33 하교 · 한국공학대 (평균) | 1.586 | 2.402 | 2.008 | 1.180 |
| 시흥33 하교 · 한국공학대 (≥3 비율) | 8.9% | 46.6% | 30.8% | 0.4% |
| 시흥1 하교 · 이마트 (평균) | 1.174 | 1.100 | 1.020 | 1.000 |
| 시흥1 하교 · 이마트 (≥3 비율) | 5.4% | 1.2% | 0.0% | 0.0% |

시흥1은 GBIS가 도착 시점에 거의 항상 1을 준다(17시 91.2%, 18시 98.0%). 해당 차량들이
3~4를 보고할 능력은 있다(모든 차량에 max 3~4 기록 존재). 현장 관측은 이마트 도착
시점에 이미 만차다. 즉 이 노선·승차점 조합에서는 신호가 현실을 반영하지 못한다.
어떤 임계값도 1을 혼잡으로 만들 수 없다.

## 설계

### ① 통계량: 평균 → 혼잡 비율

표시 근거를 "이 시간대 도착 버스 중 혼잡(≥3) 비율"로 바꾼다. 비율은 0에서 시작해
압축되지 않으므로 버킷 병합을 견딘다. 평균이 1을 하한으로 갖는 문제가 사라진다.

`bus_crowding_stats`에 등급별 표본 수 `c1, c2, c3, c4`를 추가한다. 비율과 평균 모두
이 분포에서 파생되므로 `avg_crowded`는 호환용으로 유지하되 표시에는 쓰지 않는다.

### ② 집계 단위: 로그 → 차량 접근

나이틀리 재계산이 `(route_id, stop_id, plate_no)`별로 20분 이상 공백을 경계 삼아
접근을 나누고, 접근당 `arrive_in_seconds`가 가장 작은 관측 1건만 표본으로 쓴다.
정류장에 가장 가까웠을 때의 값이 승차 시점 상태에 가장 가깝다.

### ③ 라벨 임계 (비율 기준)

| 혼잡 비율 | 라벨 |
|---|---|
| < 5% | 여유 |
| 5% 이상 15% 미만 | 보통 |
| 15% 이상 35% 미만 | 붐빔 |
| 35% 이상 | 매우 붐빔 |

실측 대입 결과: 시흥33 하교 17시 46.6% → 매우 붐빔, 18시 30.8% → 붐빔,
16시 8.9% → 보통, 19시 0.4% → 여유.

히트맵 칸은 2시간을 유지한다(24칸은 390px 뷰포트를 넘는다). 다만 요약 문장의 피크는
1시간 해상도로 계산해 "평일 17시가 가장 붐벼요"까지 짚는다.

### ④ 실시간 도착 칩

단일 차량의 실측이라 평균 문제가 없다. `1 여유 / 2 보통 / 3 혼잡 / 4 매우혼잡`을
유지한다. 현재 `BusPanel.CROWDED_META`는 4를 "혼잡", `ArrivalRow.CROWDED_KIND`는
"매우혼잡"으로 표시해 두 화면이 어긋나 있다. 단일 모듈로 통일한다.

### ⑤ 노선별 보정 `bus_crowding_calibrations`

```
id, bus_route_id, bus_stop_id, day_type, hour_from, hour_to,
min_level smallint,   -- 이 조건에서의 표시 최소 등급
reason   text NOT NULL,
created_at
```

원천 로그와 사전집계는 건드리지 않는다. 표시 시점에만 하한을 건다. `min_level`이
원시값보다 낮으면 아무 일도 일어나지 않는다(하한이 값을 낮추지 않는다).

시흥1 하교·이마트·평일 16~19시에 `min_level = 3`,
`reason = '현장 관측: 이마트 도착 시점 이미 만차. GBIS 91~98%가 값 1로 미반영(2026-08-02 확인)'`.

**출처 구분이 필수다.** 이 값은 센서 관측이 아니라 사람이 넣은 단언이다. 그대로 섞으면
관측값인 척하게 된다. 보정이 실제로 값을 올린 경우 응답에 `estimated: true`를 싣고,
화면은 `붐빔 · 경험 기준`처럼 출처를 표기한다. `reason`은 NOT NULL이라 왜 넣었는지가
DB에 남는다.

## 구성 요소와 경계

| 단위 | 책임 | 의존 |
|---|---|---|
| `bus_crowding_stats.py` | 접근 단위 dedup + 등급 분포 집계 | `bus_crowding_logs` |
| `crowding_calibration.py` (신규) | 보정 규칙 조회·적용, `estimated` 판정 | `bus_crowding_calibrations` |
| `crowding_flow.py` | 분포 → 비율 변환, 보정 적용, 응답 조립 | 위 둘 |
| `crowdingLevel.js` (신규, 프런트) | 비율 → 라벨, 원시 등급 → 라벨 (단일 출처) | 없음(순수) |
| `crowdingSummary.js` | 2시간 히트맵 + 1시간 피크 문장 | `crowdingLevel` |

프런트의 라벨 규칙이 `crowdingPalette.crowdedLabel`, `BusPanel.CROWDED_META`,
`ArrivalRow.CROWDED_KIND` 세 곳에 흩어져 있는 것이 ④의 불일치를 만들었다.
`crowdingLevel.js` 하나로 모은다.

## 데이터 흐름

```
bus_crowding_logs
  → (나이틀리) 접근 dedup + 등급 분포 → bus_crowding_stats(c1..c4)
  → crowding_flow: 비율 계산 → 보정 적용(min_level) → points[{ratio, level, estimated}]
  → 프런트: crowdingLevel.labelFromRatio → 요약 문장 / 히트맵

GBIS 실시간 → arrivals.crowded(1~4) → 보정 적용 → 칩(crowdingLevel.labelFromLevel)
```

## 오류 처리

- `bus_crowding_calibrations` 테이블 미존재(마이그레이션 미적용)면 보정 없이 동작한다.
  `crowding_flow`의 기존 `_compute_from_precomputed` 폴백과 같은 방식으로 삼킨다.
- `c1..c4`가 모두 NULL인 기존 행(마이그레이션 직후~첫 나이틀리 이전)은 비율을 계산할 수
  없다. 이 경우 해당 버킷을 `ratio: null`로 두고 라벨을 `정보 없음`으로 표시한다.
  평균으로 대체 추정하지 않는다 — 그게 지금 문제의 원인이다.
- 표본이 적은 버킷(접근 10회 미만)은 비율의 분산이 커서 오해를 만든다. `ratio`는 주되
  라벨은 `정보 부족`으로 표시한다.

## 테스트

- 집계 dedup: 같은 plate의 연속 로그가 1표본으로 접히고, 20분 이상 공백이면 2표본
- 접근 대표값: `arrive_in_seconds`가 가장 작은 관측이 선택됨
- 비율 임계 경계: 4.9 / 5.0 / 14.9 / 15.0 / 34.9 / 35.0
- 보정: 조건 밖 미적용, 원시값이 이미 높으면 하한이 값을 낮추지 않음, `estimated` 판정
- 표본 부족(<10) 시 `정보 부족`
- 실시간 칩 라벨이 `BusPanel`과 `ArrivalRow`에서 동일
