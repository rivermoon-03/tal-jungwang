# 통학 버스 정보 기준점 분리 및 화면 개선

작성일: 2026-08-01
상태: 프로덕션 배포 및 DB 마이그레이션 완료

## 문제 상황

1. 하교 목록에 학교 주변 출발과 시흥시청 이후 이동이 섞여 목적지별 정보 가치가 낮았다.
2. 이마트와 시흥터미널을 모두 `학교`로 표시해 실제 승차점을 구분할 수 없었다.
3. 노선에 `gbis_route_id`가 있다는 이유만으로 실시간 노선으로 취급했다. 그 결과 6502 하교처럼 시간표만 제공해야 하는 노선도 실시간 정보 없음으로 보였다.
4. 같은 노선의 시간표와 실시간이 서로 다른 정류장을 뜻하는데 하나의 상태처럼 합쳤다.
5. 홈과 시간표에서 노선을 열었을 때 서로 다른 상세 화면과 선택 규칙을 사용했다.
6. 버스·지하철·셔틀 탭 상태와 URL 상태가 어긋나 탭을 눌러도 버스로 되돌아왔다.
7. 탭과 콘텐츠가 애니메이션 없이 교체되거나 일부 전환은 지나치게 느렸다.

## 정보 유형별 최종 표시 정책

원본 시간표 행의 존재와 사용자에게 시간표로 제공할 수 있는지는 구분한다. 시흥1과
시흥33의 기존 시간표 행은 노선 운행 참고 데이터일 뿐, 현재 통학 화면에서 보장된
출발 시간표가 아니므로 `bus_information_sources`에는 연결하지 않는다.

| 정보 구성 | 목록 카드 왼쪽 시간열 | 카드·상세 구성 |
|---|---|---|
| 실시간만 있음 | 대표 승차점의 `N분` 또는 `곧` | 실시간 source만 표시하고 시간표 영역은 렌더링하지 않음 |
| 시간표만 있음 | 다음 출발까지 `N분`과 `HH:MM` | 시간표 source만 표시하고 실시간 영역은 렌더링하지 않음 |
| 같은 정류장에 둘 다 있음 | 실시간 도착을 우선, 없으면 다음 시간표 | 같은 정류장 아래에서 실시간과 시간표를 별도 행으로 표시 |
| 서로 다른 정류장에 둘 다 있음 | 실제 승차 기점의 시간표를 우선 | 정류장명을 붙인 독립 섹션으로 표시하고 두 값을 합치지 않음 |
| 실시간 승차점이 여러 개임 | source 정렬상 첫 승차점의 실시간 | 정류장별 실시간 블록을 분리 |
| 현재 값이 없음 | `현재 도착 정보 없음`, `금일 종료`, `운행일 확인` | `정보 보기` 같은 자리표시자는 사용하지 않음 |

## 원인

### 노선 단위 속성으로 정류장 단위 능력을 추론

`bus_routes.gbis_route_id`는 노선이 GBIS에 존재한다는 뜻일 뿐 현재 통학 맥락의 특정 정류장에서 실시간 정보를 보여줄 수 있다는 뜻은 아니다. 기존 수집기와 프론트는 이 값을 실시간 가능 여부로 확대 해석했다.

### 통학 목적과 정보 기준점의 혼용

`등교/하교`, `서울 방면`, `이마트 출발 시간표`, `시흥시청 도착 예정`은 서로 다른 축이다. 기존 모델은 노선과 한 쌍의 `stopId/realtimeStationId`만 가져 이 관계를 표현할 수 없었다.

### 프론트 하드코딩

노선별 통학 맥락이 `busCommuteContext.js`에 복제되어 DB·GBIS 변경과 어긋날 수 있었다. 특히 3401·5602의 관측 방향을 잘못 연결할 여지가 있었다.

### 탭 상태 이중 관리

`history.replaceState()`는 `popstate`를 발생시키지 않는데 URL만 변경했다. 이전 query 상태가 새 mode를 다시 덮어 탭이 되돌아갔다.

## 구현한 해결책

### DB와 백엔드

- `bus_commute_contexts`: 사용자 선택 의도인 하교 방면과 등교 출발지를 저장한다.
- `bus_information_sources`: 각 맥락의 시간표 또는 실시간 기준 정류장, 역할, 진행 방향, 화면 라벨을 저장한다.
- `bus_realtime_targets`: 수집 대상을 `노선 + 정류장 + 진행 방향`으로 명시한다.
- `GET /api/v1/bus/commute-contexts?category=...&group=...`: 여정과 정보 source를 함께 반환한다.
- 수집기는 더 이상 `bus_stop_routes`와 공유 GBIS route ID만으로 대상을 추론하지 않는다.
- 실시간 응답에 `travel_direction`을 포함해 같은 노선의 반대 진행 방향을 거를 수 있게 했다.

프로덕션 적용 SQL은 `scripts/prod_migration_20260801_bus_information_sources.sql`이다. 2026-08-01 배포 직후 코드가 DB보다 먼저 반영되어 `UndefinedTableError`가 발생했고, 같은 날 이 SQL을 단일 트랜잭션으로 적용했다.

### 정보 구조와 UI

- 하교: `정왕역 방면`, `시흥시청 방면`, `서울 방면`
- 등교: `서울 출발`, `시흥시청 출발`
- 한 노선이 여러 목적에 맞으면 여러 그룹에 중복 노출한다.
- 목록 카드 안에서 source별 요약 행을 분리한다. 예: `시흥터미널 승차 · 시간표`, `이마트 승차 · 실시간`.
- 6502 하교는 `이마트 승차 · 시간표` 한 행만 렌더링한다.
- 상세 화면도 source별 독립 섹션을 사용하며 정류장명과 정보 종류를 섹션 제목에 붙인다.
- 홈과 시간표는 모두 `ScheduleDetailModal`을 사용한다. 진입 위치에 따라 최초 통학 맥락만 다르다.
- 프론트에는 그룹 이름만 남기고 노선 포함 여부와 source 매핑은 백엔드 API를 단일 출처로 사용한다.

### 탭과 모션

- 탭 클릭 시 React mode, query state, 저장 mode, URL을 함께 갱신한다.
- press 90ms, 기본 전환 110ms, 콘텐츠 진입 120ms, sheet 140ms로 정리했다.
- `prefers-reduced-motion: reduce`에서는 관련 토큰을 0ms로 낮춘다.
- `다가오는 학사일정` 제목의 `0.14em` 자간을 `-0.02em`으로 줄였다.

## 실제 해결 여부

로컬 코드와 자동 테스트 기준으로 다음을 확인했다.

- 통학 source 모델 및 방향별 수집 대상 테스트
- 3400의 시흥터미널 시간표와 이마트 실시간 분리
- 3401의 이마트 시간표와 시흥시청 실시간 분리 계약
- 6502 하교 시간표 전용 카드
- 3401·5602의 복수 방면 노출
- 홈 카드와 시간표 카드의 공용 상세 사용
- 버스·지하철·셔틀 탭 URL/상태 동기화
- 90~140ms 모션 토큰과 reduced-motion
- 학사일정 제목 자간

초기 프로덕션 DB에는 context 19개, information source 29개, enabled realtime target 12개가 반영됐다. 6502 하교 realtime target은 0개이며, 하교 서울 방면과 등교 서울 출발 API가 실제 데이터와 함께 HTTP 200을 반환하는 것을 확인했다.

`scripts/prod_migration_20260801_bus_source_policy_corrections.sql`을 프로덕션에

context 1개 upsert였다. 최종 상태는 context 20개, information source 28개,
enabled realtime target 14개다.

99-2 realtime target은 `224000861`, `224000513` 두 정류장 모두 enabled이며

프론트 검증은 전체 112개 파일·1,261개 테스트, ESLint, 프로덕션 빌드를 통과했다.
백엔드 변경 관련 API·migration 테스트 6개를 통과했다. 백엔드 전체 241개 테스트는
로컬 PostgreSQL·Redis가 없는 실행 환경에서 42% 이후 health 검사 구간이 대기해
180초 제한으로 종료됐으며, 이 변경과 관련된 실패는 관찰되지 않았다.

### 프로덕션 브라우저 상세 검증 후속 수정

첫 병합 후 실제 브라우저에서 서울·월곶역 탭과 99-2 상세를 다시 확인했다. 목록은
의도대로 동작했지만 실시간 전용 상세 헤더에 `버스 시간표`가 남고, 복수 실시간
source의 과거 이력 설명이 첫 정류장명을 재사용하는 문제를 추가로 발견했다.

- 시간표 source가 하나도 없으면 상세 헤더를 `버스 실시간 정보`로 표시한다.
- source의 `station_label`을 각 실시간 블록 설명에 직접 전달한다.
- history-preview의 `stop_id`를 실시간 ETA뿐 아니라 과거 이력과 통계 정류장 필터에도
  적용해 시흥터미널 기록이 이마트 블록에 섞이지 않게 했다.
- 상세가 네 번째 하교 그룹인 `월곶역 방면` API도 직접 로드하도록 확장했다.

테스트를 통과했다. 후속 PR #85 배포 뒤 같은 브라우저 시나리오로 최종 확인했다.

- 시흥1 목록: 실시간만 표시하고 시간표를 표시하지 않음
- 3400 목록: 시흥터미널 다음 출발 `N분`과 `HH:MM` 표시
- 99-2 목록: 월곶역 방면에서 시흥터미널·이마트 실시간 source 둘 다 표시

### 배포 직후 장애와 운영 후속 조치

- 증상: `GET /api/v1/bus/commute-contexts`가 `relation "bus_commute_contexts" does not exist`로 500을 반환했다.
- 직접 원인: 새 백엔드 코드가 새 테이블을 조회했지만 프로덕션 SQL이 아직 적용되지 않았다.
- 구조적 원인: `backend/migrate.py`는 이름과 달리 DB 연결만 확인하고 Alembic 또는 SQL migration을 실행하지 않는다.
- 복구: 프로덕션 SQL을 `ON_ERROR_STOP=1`과 내부 트랜잭션으로 적용하고 DB seed와 실제 API를 검증했다.
- 남은 위험: 향후 스키마 변경도 코드와 DB의 배포 순서가 어긋날 수 있다. 자동 migration 도입 전에는 배포 체크리스트에서 DB migration을 백엔드 배포보다 먼저 수행해야 한다.

### 승차 지점 문구 후속 통일

시간표 source의 `출발`과 실시간 source의 `도착`은 정보 취득 방식의 차이를 노출해,
3400처럼 서로 다른 승차 정류장을 함께 보여줄 때 출발지와 목적지로 오해할 수 있었다.
사용자 행동을 기준으로 다음처럼 통일한다.

| source 역할 | 화면 문구 | 비고 |
|---|---|---|
| `departure` | `정류장명 승차` | 시간표 기준 승차 지점 |
| `boarding_arrival` | `정류장명 승차` | 실시간 기준 승차 지점 |
| `downstream_arrival` | `정류장명 도착` | 승차 후 중간 관측 지점이므로 유지 |

따라서 3400 서울 방면은 `시흥터미널 승차 · 시간표`, `이마트 승차 · 실시간`으로
표시한다. 3401 서울 방면은 `이마트 승차 · 시간표`와 `시흥시청 도착 · 실시간`을
구분한다. 같은 정류장의 시간표와 실시간을 함께 보여주는 20-1은 두 행 모두
`한국공학대학교 승차`로 표시하고 정보 종류 칩으로 구분한다. `서울 출발` 같은 그룹
탭, `곧 도착`·`도착 정보 없음` 같은 상태 문구, 지하철·셔틀 문구는 변경하지 않는다.

- 백엔드는 `source_role`을 기준으로 응답 라벨을 정규화해 기존 DB가 먼저 남아 있어도
  화면 계약을 지킨다.
- 초기 seed와 정책 보정 seed도 최종 `승차` 라벨을 저장한다.
- 운영 DB 보정은 `scripts/prod_migration_20260801_bus_boarding_labels.sql`을 사용한다.
  역할 조건과 끝말 조건을 함께 사용하므로 반복 실행해도 결과가 같다.
- 이 변경 브랜치에서는 SQL을 추가했으며, 실제 운영 DB 적용과 배포 후 브라우저 검증은
  별도 배포 단계에서 수행한다.

#### 수정

- `_realtime_routes_at_stop()`이 `bus_realtime_targets`(enabled + `gbis_route_id` 보유)에서
  정류장별 실시간 노선을 조회한다. 수집기 `_load_realtime_stations`와 같은 기준이므로
  캐시에 들어가는 노선 집합과 placeholder 집합이 일치한다.
- `bus_stop_routes`가 아니라 target을 기준으로 삼아, stop-route 링크가 없지만 실시간
  관측 대상인 3400 이마트 승차가 목록에서 빠지지 않는다.
- `timetable_route_ids`를 "이 정류장의 실시간 대상이 아닌 모든 노선"으로 바꿔, 시간표
  전용 승차점도 오늘 시간표 소진 시 내일 첫차 안내를 받는다.
- `resolve_stop_id()`가 GBIS station id와 내부 PK를 모두 받아 내부 PK로 정규화한다.
  해석 실패는 `BUS_STOP_NOT_FOUND`로 명시 실패한다(전 정류장 시간표 혼입 방지).
  매핑은 `bus:stop_pk:{raw}`로 캐시하고 `invalidate_bus_meta`가 함께 지운다.
- 실시간 대기 중인 노선의 시간표 폴백을 서버가 결정해 `depart_at`으로 내려준다.
  판단 근거는 `bus_information_sources`의 timetable source 존재 여부이며, 홈은 더 이상
  노선번호로 시간표를 다시 조회하지 않는다. 폴백 카드당 요청 1건도 함께 사라졌다.
- 폴백·미운행 카드 모두 상세로 진입한다.
- 이 승차점에 시간표가 아예 없는 실시간 전용 노선의 문구를 `출발 정보 없음`에서
  `현재 도착 정보 없음`으로 바꿔 정보 유형별 표시 정책과 맞췄다.

#### 홈 목록 기준을 DB로 이관

정류장이 어떤 노선을 취급하는지, 그 승차 지점을 뭐라 부르는지가 프런트
`busStationConfig.js` 상수에 복제돼 있었다(2026-08-01 감사 §프론트 하드코딩).
`get_arrivals` 응답에 두 값을 실어 목록의 근거를 DB로 옮겼다.

- `_stop_context_meta()`가 `bus_commute_contexts` + `bus_information_sources`에서
  정류장별 노선·승차 라벨·보장 시간표 여부를 한 번에 읽는다.
- 응답에 `expected_routes`(이 정류장이 취급하는 노선 전체)와 각 도착 항목의
  `boarding_label`을 추가했다. 승차 문구는 `bus_context`와 같은 `source_role`
  정규화를 거쳐 홈과 시간표가 같은 말을 쓴다.
- 홈의 "오늘 미운행" 목록이 `expected_routes` 기준으로 계산되고, `NotRunningCard`는
  더 이상 노선번호로 평일 시간표를 조회하지 않는다(같은 정책 우회 경로 제거).
  보조 문구는 `평일 HH:MM 첫차` 대신 `운행일 확인`을 쓴다.

행선지 라벨은 한 노선이 여러 방면 그룹에 속할 수 있어(3401·5602는 서울·시흥시청 양쪽)
정류장 단위로 확정되지 않는다. 응답에 넣지 않고 카드 제목은 표시용 상수를 유지한다.

정확히 일치했다. 즉 이 이관은 동작 변경이 아니라 출처 이동이다.
