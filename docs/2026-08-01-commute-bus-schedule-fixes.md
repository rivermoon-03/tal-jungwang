# 통학 버스 정보 기준점 분리 및 화면 개선

작성일: 2026-08-01
상태: 로컬 구현 완료, 프로덕션 DB 마이그레이션·배포 전

## 문제 상황

1. 하교 목록에 학교 주변 출발과 시흥시청 이후 이동이 섞여 목적지별 정보 가치가 낮았다.
2. 이마트와 시흥터미널을 모두 `학교`로 표시해 실제 승차점을 구분할 수 없었다.
3. 노선에 `gbis_route_id`가 있다는 이유만으로 실시간 노선으로 취급했다. 그 결과 6502 하교처럼 시간표만 제공해야 하는 노선도 실시간 정보 없음으로 보였다.
4. 같은 노선의 시간표와 실시간이 서로 다른 정류장을 뜻하는데 하나의 상태처럼 합쳤다.
5. 홈과 시간표에서 노선을 열었을 때 서로 다른 상세 화면과 선택 규칙을 사용했다.
6. 버스·지하철·셔틀 탭 상태와 URL 상태가 어긋나 탭을 눌러도 버스로 되돌아왔다.
7. 탭과 콘텐츠가 애니메이션 없이 교체되거나 일부 전환은 지나치게 느렸다.

## 원인

### 노선 단위 속성으로 정류장 단위 능력을 추론

`bus_routes.gbis_route_id`는 노선이 GBIS에 존재한다는 뜻일 뿐 현재 통학 맥락의 특정 정류장에서 실시간 정보를 보여줄 수 있다는 뜻은 아니다. 기존 수집기와 프론트는 이 값을 실시간 가능 여부로 확대 해석했다.

### 통학 목적과 정보 기준점의 혼용

`등교/하교`, `서울 방면`, `이마트 출발 시간표`, `시흥시청 도착 예정`은 서로 다른 축이다. 기존 모델은 노선과 한 쌍의 `stopId/realtimeStationId`만 가져 이 관계를 표현할 수 없었다.

### 프론트 하드코딩

노선별 통학 맥락이 `busCommuteContext.js`에 복제되어 DB·GBIS 변경과 어긋날 수 있었다. 특히 3401·5602의 관측 방향을 잘못 연결할 여지가 있었다.

### 탭 상태 이중 관리

`history.replaceState()`는 `popstate`를 발생시키지 않는데 URL만 변경했다. 이전 query 상태가 새 mode를 다시 덮어 탭이 되돌아갔다.

## 구현한 해결책

### DB와 백엔드

- `bus_commute_contexts`: 사용자 선택 의도인 하교 방면과 등교 출발지를 저장한다.
- `bus_information_sources`: 각 맥락의 시간표 또는 실시간 기준 정류장, 역할, 진행 방향, 화면 라벨을 저장한다.
- `bus_realtime_targets`: 수집 대상을 `노선 + 정류장 + 진행 방향`으로 명시한다.
- `GET /api/v1/bus/commute-contexts?category=...&group=...`: 여정과 정보 source를 함께 반환한다.
- 수집기는 더 이상 `bus_stop_routes`와 공유 GBIS route ID만으로 대상을 추론하지 않는다.
- 실시간 응답에 `travel_direction`을 포함해 같은 노선의 반대 진행 방향을 거를 수 있게 했다.

프로덕션 적용 SQL은 `scripts/prod_migration_20260801_bus_information_sources.sql`이다. 이 문서 작성 시점에는 프로덕션에 실행하지 않았다.

### 정보 구조와 UI

- 하교: `정왕역 방면`, `시흥시청 방면`, `서울 방면`
- 등교: `서울 출발`, `시흥시청 출발`
- 한 노선이 여러 목적에 맞으면 여러 그룹에 중복 노출한다.
- 목록 카드 안에서 source별 요약 행을 분리한다. 예: `시흥터미널 출발 · 시간표`, `이마트 도착 · 실시간`.
- 6502 하교는 `이마트 출발 · 시간표` 한 행만 렌더링한다.
- 상세 화면도 source별 독립 섹션을 사용하며 정류장명과 정보 종류를 섹션 제목에 붙인다.
- 홈과 시간표는 모두 `ScheduleDetailModal`을 사용한다. 진입 위치에 따라 최초 통학 맥락만 다르다.
- 프론트에는 그룹 이름만 남기고 노선 포함 여부와 source 매핑은 백엔드 API를 단일 출처로 사용한다.

### 탭과 모션

- 탭 클릭 시 React mode, query state, 저장 mode, URL을 함께 갱신한다.
- press 90ms, 기본 전환 110ms, 콘텐츠 진입 120ms, sheet 140ms로 정리했다.
- `prefers-reduced-motion: reduce`에서는 관련 토큰을 0ms로 낮춘다.
- `다가오는 학사일정` 제목의 `0.14em` 자간을 `-0.02em`으로 줄였다.

## 실제 해결 여부

로컬 코드와 자동 테스트 기준으로 다음을 확인했다.

- 통학 source 모델 및 방향별 수집 대상 테스트
- 3400의 시흥터미널 시간표와 이마트 실시간 분리
- 3401의 이마트 시간표와 시흥시청 실시간 분리 계약
- 6502 하교 시간표 전용 카드
- 3401·5602의 복수 방면 노출
- 홈 카드와 시간표 카드의 공용 상세 사용
- 버스·지하철·셔틀 탭 URL/상태 동기화
- 90~140ms 모션 토큰과 reduced-motion
- 학사일정 제목 자간

프로덕션에서 해결됐다고 단정할 수는 없다. 마이그레이션과 애플리케이션 배포 후 모바일·태블릿·PC에서 실제 API 응답과 화면을 다시 확인해야 한다.

## 배포 전·후 확인 순서

1. 스테이징 DB에서 마이그레이션을 트랜잭션으로 검증한다.
2. context/source/target seed 행 수와 6502 하교 realtime target 부재를 확인한다.
3. 백엔드를 먼저 배포해 context API와 collector cache payload를 확인한다.
4. 프론트를 배포해 3400, 3401, 5200, 5602, 6502의 목록과 상세를 확인한다.
5. 홈과 시간표에서 같은 노선을 열어 동일한 상세 본문인지 비교한다.
6. 모바일·태블릿·PC 및 reduced-motion 환경에서 전환과 레이아웃을 확인한다.
